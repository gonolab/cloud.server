# v1 Scope

This document records the scope decisions for the first release of the rewrite. Anything not
listed under "In scope" is deferred until after v1.

## Supported clients

| Client | How compatibility is verified |
|---|---|
| Nextcloud desktop | `nextcloudcmd` sync scenarios in CI |
| Nextcloud mobile (Android, iOS) | Manual test checklist |
| Gono client | The client is being rewritten as well and follows the server's capabilities |
| Generic WebDAV clients (Finder, Windows Explorer, rclone, Cyberduck) | `litmus` in CI |

## In scope

- **WebDAV core**: `OPTIONS`, `PROPFIND`, `GET`, `HEAD`, `PUT`, `MKCOL`, `COPY`, `MOVE`,
  `DELETE`, `PROPPATCH`, `LOCK`, `UNLOCK`, served through dav-server-rs.
- **Nextcloud protocol surface**:
  - `status.php`, capabilities, and the OCS user endpoints the clients call at startup.
  - Chunked upload v2 (`/remote.php/dav/uploads/...`).
  - Login Flow v2 with an explicit consent page; every device gets its own newly minted app
    password.
  - Live properties (`oc:fileid`, `oc:permissions`, `oc:favorite`, ...) and `OC-*` response
    headers.
  - Directory ETag propagation: any change updates the ETag of every ancestor collection.
  - Favorites through `PROPPATCH` and the `filter-files` REPORT (used by the mobile apps).
- **Multiple users** with per-app-password mount scopes (`view` or `full`).
- **notify_push** for real-time change notifications.
- **Web admin UI**: server overview, accounts (create, enable and disable, admin role, display
  name, web login password, delete) and app passwords.
- **CLI**: `init`, `serve`, `config check`, user and app password management (including
  promoting and demoting admins and changing display names), and a manual `rescan` command.
- **Packaging**: release archives for Linux (x86_64 and aarch64, glibc 2.28 or newer) and
  macOS (Apple silicon and Intel), a hardened systemd unit, a launchd job and an install script
  for installs, upgrades and uninstalls (see `docs/deployment.md`).

## Out of scope for v1

- `sync-collection` REPORT. The Gono client will be adapted to the v1 server capabilities.
- Built-in TLS. HTTPS is terminated by a reverse proxy.
- Automatic detection of changes made directly in the data directory.
- Migration from the legacy v0.1.x releases. There are no deployments to migrate.
- Release builds for Linux without glibc (Alpine and other musl distributions), Windows, and a
  container image. The server builds from source on other Unix systems.
- Sharing and public links, calendar and contacts, previews and thumbnails, file versions, trash
  bin, and end-to-end encryption.

## Decisions

### Data directory ownership

The data directory belongs to the server. All changes are expected to go through WebDAV. If an
administrator changes files out of band (SSH, Samba, rsync, ...), they must run
`gono-cloud rescan` for the affected user or path. Until then, clients may not see those changes.

### Credentials

- Each user has a **web login password**, chosen by the user and stored as an Argon2 hash. It is
  used only for Login Flow v2 and the web admin UI.
- Devices authenticate with **app passwords**. They are high-entropy random tokens generated by
  the server and stored as SHA-256 hashes. They are minted per device through Login Flow v2, the
  CLI, or the web admin UI.
- The web admin UI uses session-based login with the web login password. App passwords cannot
  access it.

### Deployment

The server listens on plain HTTP on a loopback address. A reverse proxy (nginx or Caddy)
terminates HTTPS. The public origin is configured explicitly. Client IP addresses are taken from
forwarding headers only when the request comes from a configured trusted proxy.

### Packaging

The Linux binaries are linked against glibc 2.28 with cargo-zigbuild instead of being built
against the release runner's newer glibc, so one build covers RHEL 8, Debian 10, Ubuntu 20.04
and later. Static musl builds were not added: musl's allocator is markedly slower under
concurrent load, and the glibc baseline already covers the supported distributions. The Intel
macOS build is cross-compiled on Apple silicon, which costs one more build job.

The server runs as a dedicated system user (`gono-cloud`, `_gono-cloud` on macOS) that owns the
database and the data directory. The configuration belongs to root and is only readable by the
service. The command line refuses to run as root against such an installation, because files it
created would be unusable for the service.

## Deferred

Decided for after v1:

- Making the failed-login rate limits, the upload, Login Flow and session lifetimes, and the
  interval at which the server polls the change log for `rescan` changes configurable. They are
  constants today.
- Rotating log files. Under systemd the journal rotates the logs; the launchd job on macOS and
  `logging.file` append to one file without rotation.

## Open questions

These are resolved by testing against real clients, not by decision:

- Which `status.php` and capabilities fields the clients require (for example `productname` and
  `version`). The default is to report the project's own product name.

  Findings so far (2026-11-09): `status.php` reports `productname` `Gono Cloud` and `version`
  `30.0.0.0` (`versionstring` `30.0.0`), the Nextcloud release whose client protocol is
  implemented. The clients select features by `version` (the desktop client uses Login Flow v2
  from 16.0 on and warns about versions it no longer supports), not by `productname`.
  `nextcloudcmd` 4.0.6 (Ubuntu 26.04) reads `status.php`, the capabilities and
  `/ocs/v1.php/cloud/user` and completes every sync scenario of
  `acceptance/scripts/nextcloudcmd-scenarios.sh` with these values; no desktop behavior
  depends on `productname`. The mobile apps are not verified yet; `docs/mobile-checklist.md`
  step 1.1 checks that they accept the server. If one of them requires a specific
  `productname`, that is a decision for the maintainers, not a default to change silently.
- The exact set of OCS endpoints the mobile apps call, and which of them can return empty
  results. Implemented: `cloud/capabilities`, `cloud/user`, `cloud/users/<own id>`,
  `core/apppassword` (`DELETE`) and an empty `core/navigation/apps`; everything else answers
  an OCS 404. `nextcloudcmd` 4.0.6 calls only `status.php`, the capabilities and
  `cloud/user`. The mobile checklist records the failed requests of the apps.
